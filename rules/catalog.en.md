# Rule catalog

Each rule lists why it exists, where it is enforced and how to recover when it blocks you. This file is generated by `wb-rules render --write`; do not edit it by hand.

## Git and branches

### lane-own-branch

A lane commits only to its own lane branch. It does not push, switch branches or merge into the integration branch.

- Why: Lanes writing to one branch overwrite each other and nobody can tell which lane changed what.
- Enforced in: `hooks/scripts/safety/git-guard.mjs`
- If blocked: Go back to your lane branch and commit there. To get the latest integration work, only merge the integration branch into your own branch. The controller lands the lane.

### no-force-push

Force pushes and whole-repository pushes (--all, --mirror) are not allowed for anyone.

- Why: A force push erases other people's commits, and a whole-repository push also sends protected branches.
- Enforced in: `hooks/scripts/safety/git-guard.mjs`
- If blocked: Use a normal push naming one branch. If history must be rewritten, ask the repository owner.

### protected-branch-owner-grant

Landing work on a protected branch (main and so on) needs the owner's grant. A grant works once, within a time limit, and only for the commit it was given for.

- Why: Everyone builds on protected branches. If an agent lands work by itself, unreviewed changes become the baseline.
- Enforced in: `hooks/scripts/safety/git-guard.mjs`, `skills/approve/SKILL.md`, `hooks/scripts/safety/approve.mjs`
- If blocked: The owner types `/wb:approve merge-main` in the prompt. When a gate command exists, the gate must pass for the same commit first. If the grant expired, type it again.

### gate-lock

No merging while the verification gate is running.

- Why: If the code changes while the gate runs, the result no longer belongs to a known commit.
- Enforced in: `hooks/scripts/safety/git-guard.mjs`
- If blocked: Wait for the gate to finish and try again. If the gate is stuck, ask the owner to clear the stale lock with `wb-reap --gate-lock`.

### no-destructive-git

Git commands that destroy uncommitted changes or unmerged commits (reset --hard, clean -f, branch -D, unnamed stash) do not run without confirmation.

- Why: Deleted changes cannot be recovered. An unnamed stash shares one list with other sessions and can take or drop someone else's work.
- Enforced in: `hooks/scripts/safety/git-guard.mjs`
- If blocked: Save the work in a temporary commit first. If it really must go, check the target and approve the prompt. If you need a stash, give it a unique name.

### feature-push-ask

Pushing a feature branch asks for confirmation or is blocked, depending on the setting.

- Why: A branch on the remote is visible to others, so the project decides whether agents may push.
- Enforced in: `hooks/scripts/safety/git-guard.mjs`, setting `project.git.feature_push`
- If blocked: Approve the prompt when it asks. When blocked, ask the owner to push or change `project.git.feature_push`.

### no-lane-pr-merge

A lane does not merge pull requests.

- Why: Merging is the controller's step after review.
- Enforced in: `hooks/scripts/safety/pretool.mjs`
- If blocked: Pass the request to the controller and put the PR number and state in your report.

## Processes and environment

### no-pattern-kill

Do not kill processes by name or pattern. Kill only the PIDs you started. Never kill a process that holds a protected port.

- Why: Pattern kills have taken down servers started by other jobs. Losing the owner's server stops their work.
- Enforced in: `hooks/scripts/safety/kill-guard.mjs`
- If blocked: Find the PID with `lsof -i :<port>` or your own run record and kill only that PID. Ask the owner for anything on a protected port.

### lane-ports

A lane uses only the port range assigned to it. Ports come from `wb-port`.

- Why: Two lanes on one port means one server fails to start, or a lane checks the wrong server.
- Enforced in: `bin/wb-port`, `lib/ports.mjs`
- If blocked: Lease your ports with `wb-port lease --lane <lane>` and start servers on them. On a clash, check the holder with `wb-port list`.

### headless-browser

Browsers run only in headless mode, with no window.

- Why: A window steals focus from the screen the user is working in.
- Enforced in: `hooks/scripts/safety/browser-guard.mjs`
- If blocked: Add `--headless=new` or use a headless tool. Show a window only when the owner asks.

### heavy-runs-in-slots

Full test runs, full builds, installs and browser runs go through `wb-slot`.

- Why: When heavy runs overlap across lanes the machine slows down and tests time out with false failures.
- Enforced in: `hooks/scripts/slots/slot-guard.mjs`, `bin/wb-slot`, setting `machine.slots`
- If blocked: Wrap the command: `wb-slot -- <command>`. If no slot is free it waits its turn.

## File and command safety

### resolvable-commands

Commands whose effect cannot be known before they run (a command name or target built from a variable or substitution) are blocked.

- Why: If the target is decided only at run time, the other safety rules cannot check the command.
- Enforced in: `hooks/scripts/safety/shell.mjs`, `hooks/scripts/safety/git-guard.mjs`, `hooks/scripts/safety/kill-guard.mjs`
- If blocked: Write the real value instead of the variable. If the value is long, print it first, check it, then use it directly.

### rm-inside-project

Recursive deletion (`rm -r`) is limited to checked paths inside the project folder.

- Why: Deleting the home folder, system folders or git internals cannot be undone, and a path built from an empty variable can wipe a parent folder.
- Enforced in: `hooks/scripts/safety/destructive.mjs`
- If blocked: Write the real path and run again. Ask the owner for anything outside the project.

### protected-paths

Protected paths, wb state files and wb settings are not written by agents.

- Why: If an agent could edit the grant file or the settings it could lift the safety rules itself.
- Enforced in: `hooks/scripts/safety/paths.mjs`, setting `project.protected_paths`
- If blocked: Change state files only with the `wb-*` tools. Settings are changed or approved by the owner.

### human-only-approve

`/wb:approve` works only when a person types it in the prompt.

- Why: If an agent could create its own grant, the owner grant would mean nothing.
- Enforced in: `hooks/scripts/safety/approve.mjs`, `skills/approve/SKILL.md`
- If blocked: Tell the owner which action needs the grant and ask them to type it.

### safety-fails-closed

When a safety hook cannot decide, or its settings are broken, the call is blocked.

- Why: Letting a call through without a decision drops the rules exactly when they matter.
- Enforced in: `hooks/scripts/safety/pretool.mjs`, `hooks/scripts/safety/context.mjs`
- If blocked: Run `/wb:doctor` to find the file and key, fix it, then confirm with `wb-config validate`.

## Models and briefs

### model-routing

Subagents start on the model that fits the task type. Denied models, models outside the chain and models below the floor are not used.

- Why: Tasks need different levels of judgement. Giving design or review to a weaker model lets defects through, which cost more later.
- Enforced in: `hooks/scripts/dispatch/dispatch-guard.mjs`, `bin/wb-route`, setting `routing`
- If blocked: Start again with the model `wb-route resolve <task>` names. If the limit is used up, wait for the reset instead of going below the floor.

### implementer-verifier-differ

Review and adversarial checks use a model different from the implementer. If none is available, use the same model in a fresh context and say so in the report.

- Why: A model re-checking its own output tends to repeat the same mistake.
- Enforced in: `hooks/scripts/dispatch/dispatch-guard.mjs`, `bin/wb-route`
- If blocked: Use `wb-route explain <task> --implementer <model>` to see which model is allowed and start it.

### brief-required

A lane starts from a brief that has the marker and the required sections (goal, scope, do-not, tests, report, commit).

- Why: When instructions are only spoken, scope and prohibitions drop out and a lane touches other lanes' files or leaves no report.
- Enforced in: `hooks/scripts/dispatch/dispatch-guard.mjs`, `bin/wb-check`, `templates/briefs/ko/impl.md`, setting `dispatch.brief`
- If blocked: Run `wb-check brief <file>` to see what is missing, fill it from `templates/briefs/` and start again.

### lane-cap

The number of live lanes stays within the cap (3 by default).

- Why: Too many lanes raise machine load, cause time-out failures and outrun review.
- Enforced in: `hooks/scripts/dispatch/dispatch-guard.mjs`, `bin/wb-worktree`, setting `machine.lanes.max`
- If blocked: Land finished lanes and clean up their worktrees before opening a new one. Check live lanes with `/wb:lanes`.

### lane-test-scope

A lane runs only the test files it wrote or changed. The full suite and all-package checks run once, by the controller.

- Why: If every lane runs the full suite the load stacks up, tests time out, and the same result is produced several times.
- Enforced in: `templates/briefs/ko/impl.md`, `hooks/scripts/dispatch/dispatch-guard.mjs`, `hooks/scripts/slots/slot-guard.mjs`
- If blocked: Follow the brief's test rules and run single files only. If you think the full suite is needed, say so in the report for the controller.

### report-twice

A lane writes its report to a file and also returns it in its final reply. It leaves interim notes after each large item.

- Why: Results must survive an empty reply or an interruption.
- Enforced in: `templates/briefs/ko/impl.md`, `hooks/scripts/dispatch/dispatch-guard.mjs`
- If blocked: Write what you have to the report path in the brief and attach a summary to the reply.

### base-commit

A lane checks at the start that the worktree HEAD equals the base commit in the brief, and reports before working if it does not.

- Why: Working from an old base re-fixes solved problems or makes the merge conflict larger.
- Enforced in: `templates/briefs/ko/impl.md`, `hooks/scripts/dispatch/dispatch-guard.mjs`
- If blocked: Compare `git log -1` with the brief. If they differ, merge the integration branch first or tell the controller.

## Sessions and handoff

### progress-handoff

Read `progress.md` first when a session starts and update it at the end of each unit of work. A session must not end with a stale `progress.md`.

- Why: A new session with a cleared context picks up from `progress.md` alone. If it is stale, finished work is repeated or half-done state is missed.
- Enforced in: `hooks/scripts/handoff/session-start.mjs`, `hooks/scripts/handoff/stop-guard.mjs`, `skills/pickup/SKILL.md`
- If blocked: Write what is done, in progress, next, waiting and the pitfalls into `progress.md`, commit, then stop.

### wave-checkpoint

When a wave (unit of work) ends, commit the progress record and tell the user to run `/clear`.

- Why: Long contexts hit limits and stop. A record written early lets a new session continue from any point.
- Enforced in: `hooks/scripts/checkpoint/checkpoint.mjs`, `skills/resume/SKILL.md`
- If blocked: Run `/wb:resume` to build the resume report and clear stale items first.

### token-stages

When token use reaches 90%, 95% and 99%, follow the stage rules (smaller waves, handoff every wave, final handoff then wait).

- Why: Stopping suddenly at the limit loses unrecorded work.
- Enforced in: `hooks/scripts/token-guard/check.mjs`, `skills/token-guard/SKILL.md`, setting `personal.token_guard`
- If blocked: When the notice comes, wrap up the current step and update `progress.md`. Change the thresholds with `/wb:token-guard`.

### auto-retry-default-permission

Automatic resume after a usage limit runs in the default permission mode only.

- Why: An unattended session that skips permission prompts could run risky actions with nobody watching.
- Enforced in: `hooks/scripts/auto-retry/detect.mjs`, `skills/auto-retry/SKILL.md`, setting `personal.auto_retry.permission_mode`
- If blocked: Check the schedule with `/wb:auto-retry status`. Raising the mode needs the user's explicit acknowledgement.

### terse-mode

With terse mode on, output and tool calls are reduced, but verification evidence and the final report are not.

- Why: The aim is to save tokens, not to claim results without checking.
- Enforced in: `hooks/scripts/terse/session-start.mjs`, `skills/terse/SKILL.md`, `rules/terse.ko.md`
- If blocked: Turn it off with `/wb:terse off`.

## Quality and documents

### tests-with-change

When a feature is added, changed or removed, its tests change in the same change. A defect that cannot be fixed now is recorded and marked pending, not hidden by weakening the test.

- Why: Changes without tests, tests that hold on to removed features and expectations that differ from behavior all cause trouble in the next change.
- Enforced in: `templates/briefs/ko/impl.md`, `bin/wb-defects`, `bin/wb-cases`
- If blocked: Update the tests as the brief's test rules say. Record an unfixable defect with `wb-defects add`.

### test-results-workbook

Test results are saved as a workbook and committed. A report cannot be closed without it.

- Why: "It passed" alone cannot show later what was checked and how many cases.
- Enforced in: `bin/wb-test-report`, `bin/wb-check`, `skills/test-report/SKILL.md`
- If blocked: Create the workbook with `/wb:test-report` and verify it with `wb-check test-results`.

### number-reservation

Numbered files (migrations, decision records and so on) get their number reserved before they are created.

- Why: If parallel lanes pick the same number, the merge conflicts and numbers must be reassigned.
- Enforced in: `bin/wb-number`, `lib/numbers.mjs`, setting `project.numbers`
- If blocked: Take the number from `wb-number reserve <series> --lane <lane>`. If two files already clash, renumber the later one.

### worktree-cleanup

A finished lane worktree is merged into its target and then removed. Before removal, the processes started there are stopped by PID.

- Why: Orphan processes in leftover worktrees keep using the CPU and split the handoff.
- Enforced in: `bin/wb-worktree`, `bin/wb-reap`, `skills/resume/SKILL.md`
- If blocked: Check candidates with `wb-reap` and remove with `wb-worktree remove <lane>`.

### owner-decisions-recorded

Decisions made by the owner are written down as decision records (`docs/decisions/`).

- Why: A decision made only in conversation is unknown to the next session, and the same question comes back.
- Enforced in: `skills/decide/SKILL.md`, `bin/wb-decide`, setting `project.paths.decisions`
- If blocked: Use `/wb:decide` to put the question, get the answer and write the record.

### style-per-file

Documents and screen text use the style set per file kind (`style.map`).

- Why: Without a split between plain screen text and business-style reports, readers get an inconsistent product.
- Enforced in: `skills/writing-style/SKILL.md`, `bin/wb-style`, `templates/briefs/ko/docs.md`, setting `project.style.map`
- If blocked: Check the style with `wb-style of <file>` and fix the text by the rules from `wb-style rules <style>`.

## Planned

### mockup-first

A change to screen structure shows a mockup and gets a decision before implementation.

- Why: If the structure is rejected after implementation, the whole job is redone.
- Enforced in: not built yet (added by lane L7)
- If blocked: Until the hook ships, put the mockup step into the brief yourself.

### glossary-terms

Words in screen text follow the project glossary.

- Why: Calling one concept by different names across screens confuses users.
- Enforced in: not built yet (added by lane L10)
- If blocked: Until the check ships, follow the haeyo rules and the words already on screen.

### codegraph-first

To understand code structure use the index tool first; use text search for line numbers and strings.

- Why: Answering structure questions by text search multiplies the number of calls.
- Enforced in: not built yet (added by lane L12)
- If blocked: Until the hooks ship, follow the work-location text in the brief.
