# 문체 규칙

파일 종류별 문체는 `.wb/config.json` 의 `style.map` 이 정한다. 아래는 문체별 규칙이다.

## haeyo
대상: 화면 문구, 인앱 매뉴얼, 도움말, 안내 메시지.

- 해요체로 쓴다. 「저장해요」「선택하세요」처럼 짧은 존댓말이다.
- 한 화면에는 한 가지 주제만 둔다. 주인공이 되는 동작이나 값을 앞에 둔다.
- 제목은 평서문이나 명사구로 쓴다. 「~할까요?」 같은 질문형 제목은 쓰지 않는다.
- 설명을 덧붙여 꾸미지 않는다. 버튼 이름과 안내는 동작을 그대로 말한다.
- 줄표(―, --)로 문장을 이어 붙이지 않는다. 문장을 나눈다.
- 약어와 개발자 용어는 쓰지 않는다. 프로젝트 용어 사전이 있으면 그 낱말을 따른다.
- 문구 때문에 AI가 쓴 느낌이 나면 안 된다. 「쉽고 빠르게」「강력한」 같은 말은 쓰지 않는다.

### 읽기 어려운 문장 네 가지를 쓰지 않는다
- 앞뒤 문장에 이유·결과·대조·순서·조건의 관계가 있으면 「그래서」「그런데」「다만」「~면」 같은 연결 단어로 드러낸다. 예: 「조회가 느리다. 캐시를 둔다.」 대신 「조회가 느려서 캐시를 둔다.」
- 사물과 기능에 사람의 동작(삼키다, 꼬리를 물다, 깨우다, 죽이다)을 붙이지 않고 실제로 일어나는 일을 쓴다. 예: 「에러를 삼킨다」 대신 「오류를 잡고 기록을 남기지 않는다」
- 명사를 세 개 이상 조사 없이 잇지 않는다. 조사와 어미를 넣어 푼다. 제품명처럼 굳은 이름은 예외다.
- 주어와 서술어, 꾸미는 말과 꾸밈을 받는 말 사이를 길게 벌리지 않는다. 사이에 긴 수식이 끼면 문장을 나눈다.

## report
대상: 개발 문서, 보고서, 인증 서류, 배포 문서. 독자는 개발자가 아닌 임원, 사업 담당자, 고객, 프로젝트 관리자로 본다.

- 보고서체(「~한다」「~이다」)로 쓴다.
- 현황이나 문제를 먼저 쓰고, 적용 방안, 주요 내용, 영향·고려사항 순으로 쓴다.
- 한 문장에는 한 가지 사실만 쓴다. 긴 문장은 2~3개로 나누고, 명사만 이어 붙인 문장은 풀어 쓴다.
- 확인하지 못한 내용은 「미확인」으로 표시하고 추측으로 채우지 않는다.
- 비교·조건·절차처럼 목록이 필요한 곳에만 표와 목록을 쓴다. 내용 없는 제목과 1.1.1 식 세분화는 뺀다.
- 개요·요약·결론에서 같은 내용을 표현만 바꿔 되풀이하지 않는다. 한 곳에 모은다.
- 의사결정과 관계없는 내부 구현 세부는 빼거나 부록으로 옮긴다.

### 작성 흔적을 남기지 않는다
- 작업 과정을 설명하는 문장(「분석해 보겠습니다」「검토 결과」「이제 ~를 살펴보겠습니다」「수정했습니다」)
- 사용한 명령, 프롬프트, 에이전트, 스크립트, 도구 이야기
- 「본 문서에서는」「종합하면」「결론적으로」의 반복, 「핵심은 ~입니다」 같은 빈 강조
- 문서 품질에 대한 자체 평가, 작업 로그, TODO, 내부 메모, 초안 흔적

### 과장·비유를 쓰지 않는다
두뇌, 혈관, 심장, 신경망, 레고 블록처럼, 퍼즐처럼, 엔진, 허브, 게임 체인저, 강력한, 획기적인, 혁신적인, seamless, robust, scalable. 실제 기술 용어로 쓰는 경우만 예외다.

### 근거 없는 판단은 사실로 바꾼다
「효율적이다」「최적이다」「안정적이다」「성능이 뛰어나다」「확장성이 높다」「비용이 절감된다」「생산성이 향상된다」는 수치나 근거가 있을 때만 쓴다. 없으면 실제 구조나 효과를 적는다(예: 「확장성이 뛰어나다」 → 「기능을 모듈 단위로 추가할 수 있어 기존 기능의 수정 범위가 줄어든다」).

### 개발자 용어는 업무 용어로 바꾼다

| 개발자 용어 | 권장 표현 |
|---|---|
| 파이프라인 | 처리 절차, 처리 흐름 |
| 오케스트레이션 | 작업 통합 관리 |
| glue | 연계 기능 |
| source of truth | 기준 정보 |
| bootstrap | 초기 구성 |
| plug-in 방식으로 꽂는다 | 필요한 기능을 추가할 수 있도록 구성 |
| loose coupling | 시스템 간 의존성을 최소화 |
| fail fast | 오류를 조기에 확인 |
| graceful degradation | 일부 장애 시에도 가능한 기능은 계속 제공 |
| single pane of glass | 통합 관리 화면 |

API, DB, AI, ERP, WAS 처럼 업계에서 널리 쓰는 말은 억지로 바꾸지 않는다. 꼭 필요한 전문용어는 처음 한 번만 짧게 풀어 쓴다.

### 마지막 점검
문장마다 세 가지를 묻는다. 하나라도 걸리면 고치거나 지운다.
1. 실제 회사 직원이 보고서에 쓸 표현인가?
2. 개발자가 아닌 사람이 읽어도 바로 이해하는가?
3. 이 문장이 없어도 뜻이 같은가?

## plain
대상: 위 두 가지에 해당하지 않는 파일.

- 짧은 문장으로 쓴다. 기존 파일의 문체와 용어를 따른다.
- 이모지와 장식 표현을 쓰지 않는다.
